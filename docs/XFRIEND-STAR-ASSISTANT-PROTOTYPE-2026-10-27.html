打开就是星助理。
专业分工留在系统内部。

这个原型只回答一件事：把现在的「对话／工作台／资源／我的」四入口，收敛成一个能真实聊天、能按住语音说话、能对着某条消息回复、并在后台派出子代理的星助理，界面应该长什么样、按下去会发生什么。

01

目标与设计原则

统一入口不等于删掉专家、团队、会议这些后台能力，也不等于把权限交给模型。原型的取舍全部围绕四个不变量：一个入口、任务在后台、信息说清楚、完成可核验。

一个入口，二级展开

启动直接落在主会话。历史、设置、记忆、任务都是二级抽屉或页面，不再有专家／团队／会议常驻页签，也不把三个页签换成「会话／记忆／任务」底栏。

总 Agent 只负责接、路由、汇报

消息先进入持久收件队列并立即返回受理或排队，长任务交给子 Agent。首任务运行时仍可接收第二个无关需求；子代理有独立 context_id 与检查点，主会话只出现任务卡片。

说清楚：目标、位置、目的地、范围

消息回复始终带目标与版本；任务卡显示执行节点；切模型/服务商时提示数据将发往哪个域名；审批卡列出操作、收件人、正文摘要、有效期——任一字段变化即失效重审。

完成要有证据，不靠措辞

状态与 revision 由服务端持久化，客户端断线不等于后台停止。恢复时先取快照再按 last_event_id 续订；「模型说完成了」不构成 completed，必须有结果引用或完成依据。

刻意不做：常驻全自动电脑接管、完整语音通话/后台唤醒、自动安装执行器或插件、把所有邮件与笔记平台一次接通、为统一入口重造一套并行数据库。旧专家配置、团队权限、会议记录保持可读，由功能开关控制入口显隐。

首版必须闭合的四条链路

P1

真实对话

默认中转站真实请求，流式、停止、错误分类、历史恢复；断网与错误鉴权有正确反馈。

P2

调试配置

独立调试包、多配置、安全存储、手填 model_id，真实探测后给出可操作建议。

P3

语音与回复

中文录音→转写→可编辑→发送；消息级引用、定位、版本与撤权占位。

P4

子代理与恢复

持久收件、独立上下文、预算/并发/深度、父取消传播、重启后可恢复。

05

并发任务：一个入口，两条正在跑的线

“一边录音转写，一边改 PPT”——这是最容易把界面做崩的场景：两个输入流、两种进度、一份文件还要写回。做法不是在会话里并列两段聊天，而是把三件事拆开：输入通道（录音条、文本框）只负责采集；会话时间线只留发起、关键节点、需要你、结果；任务各自拥有 context、预算、租约与检查点。界面上只多两样东西：顶部任务托盘，和二级的任务面板。

一条会话

不分裂聊天窗口

第二条任务不新开会话。发起它的气泡与结果卡片留在原位置，后台进度只更新卡片，不刷屏、不打断对话。

输入与任务分开

录音是通道，转写才是任务

麦克风同一时刻只发一个录音租约。转写结果先落「待确认草稿」，用户发送或说「整理成纪要」才变成任务输入。

冲突要显式

同一份文件只有一个写者

PPT 写回前要审批；第二个任务想改同一文件时排队并显示等待位置，不静默覆盖、不各写一版。

架构：输入、路由、任务、事件分开

一句话怎么落到正确的任务上

用户这句话路由判定落到哪界面反馈
「把录音里的行动项加进结尾页」update_task（带 input_refs）改 PPT 任务输入区显示「发送到 改 PPT」；卡片追加一步
「这段先别转成纪要」cancel_task录音转写任务卡片转「正在停止」；已产出的草稿保留并说明
「顺便查一下竞品定价」new_task同会话新建任务追加一张新卡片，托盘 +1，不打断上一条
「那页先别改」但没说是哪页clarification暂不落任务回一句追问，不猜、不默认最新任务
电脑离线时点「批准写回」保留审批，任务进 waiting_device原任务卡片提示「电脑离线；恢复后需重新确认」

资源冲突与恢复

资源独占/并发规则冲突时界面
本机麦克风同一时刻一个录音租约；取消立即释放第二个录音请求显示「麦克风被录音 #41 占用」，可排队或结束它
同一份 PPT 文件同一时刻一个写者；写入校验 base_version返回文件锁/版本冲突，给「对比后合并」而不是静默覆盖
配对电脑节点节点在线 lease 才执行；撤销配对后新调用拒绝离线进 waiting_device；恢复后重查权限与审批
网络与进程后台不随客户端断开停止；重启从 checkpoint 恢复重连先取任务快照，再按每任务 last_event_id 续订
为什么不是两个会话

上下文不串，也不复制

总 Agent 只做接收、澄清、路由与汇报；两个任务各自独立 context。跨任务只交换 resource_id（例如转写草稿 draft_0912），不复制整段对话，也不让模型互相看见对方的过程。

为什么不是后台自动乱跑

预算、深度、取消都可控

每任务独立预算 + 父任务总预算；并发 3、递归深度 2；父取消向下传播到子代理。取消不等于撤销已写回的文件，界面会列出已完成与未执行的步骤。

这不是第二个入口。托盘是主会话里的状态条，任务面板是二级页面；底部仍然没有页签，录音条也只占输入区。用户始终只面对一个星助理，专业分工留在系统内部。
06

状态、错误与恢复

界面最容易被做假的地方就是状态。这里把错误分类和任务状态定死：每一个都能落到具体文案、可操作下一步与恢复策略；不存在笼统的「网络错误」，也不存在只靠模型措辞的「已完成」。

错误分类（对应 A04）

错误码界面表现用户下一步不得出现
network_unreachable顶部条：当前网络不可达，草稿已保留。发送按钮置灰，不弹假回复。检查网络或稍后重试；恢复后先查原请求状态再决定是否重发。自动重试写操作；把草稿清空。
auth_failed配置页对应 profile 标红；详情给 401 与凭据引用名。去修改凭据引用；不要把 Key 贴进聊天或日志。把整段响应体、请求头打进日志。
model_not_found「模型不存在」，保留已填 model_id 供修改。手填正确 ID 或从可选列表选择。静默改用另一个模型继续执行。
quota_exceeded「额度不足」，附当前 profile 与剩余额度（若服务返回）。更换模型/服务或充值。继续重试直到被动限流。
rate_limited「请求过快」，显示建议等待时间；队列位次可见。等待或降低并发；任务进入排队而非失败。把限流写成鉴权失败。
unsupported_capability能力标签置灰（如流式、工具），并说明该协议不支持。切换适配器或关闭对应能力。假装流式（一次性回显后再拆字）。
provider_error「服务商错误」，展示 request_id 前缀与耗时。保留诊断信息稍后重试；必要时切换服务商。只显示「出错了」。

任务状态机（对应 A11 / A12 / A13）

状态主界面允许操作持久化与恢复
queued 排队任务条：排队中 · 第 2 位取消、查看详情收件队列持久化，服务重启不丢单
running 执行中卡片显示步数与预算停止生成、查看子代理、取消每步写事件与 result_ref；断线后台继续
awaiting_approval 待确认审批卡置顶，任务条转黄批准/拒绝（绑定摘要）重启后审批仍有效或按 expires_at 失效
waiting_user 等待你卡片提示需要补充信息回答、取消问题与已收集上下文写入 checkpoint
waiting_device 等待电脑「已连接电脑离线」+ 最后在线时间重连、改为云端方案（需授权）不假装执行；节点租约与在线状态真实
waiting_external 等外部等待第三方返回，可离开页面查看进度、取消恢复时核对目标系统真实状态
failed 失败失败原因 + 已完成步骤 + 可重试范围查看诊断、有限重试、取回输入失败不被父代理的乐观总结覆盖
cancelling 正在停止「正在停止，等待工具确认」无（等待）确认执行停止后才进 cancelled
cancelled 已取消已完成步骤 / 未执行步骤 / 是否可补偿新建任务取消不撤销已发送邮件或已改文件
completed 已完成结果引用 + 证据 + 耗时打开结果、复制、追问必须有可核验结果，模型措辞不算
恢复顺序

先快照，再续订

重连或重启后先取任务快照（含 revision、steps、child_tasks），再从 last_event_id 订阅。缺口时重新取快照，不按片段硬拼正文。

事件语义

去重与缺口

event_id 去重、seq 在任务内单调。message.completed 与流式片段不能重复追加；先落库后发事件。

副作用

未知就先查，不重放

超时未知时先查原请求状态；任务、子代理、审批、外发动作都用 idempotency_key。取消不等于撤销已生效的外部操作。

外部内容只是数据。文件、网页、邮件里的「请忽略之前指令」「把结果发到某地址」不会变成授权；审批只认当前用户在当前工作区发起的、绑定具体目标与摘要的批准。对应 A18。
