Direction 03 · Engine strategy

完整 DSH 引擎不整包塞进手机：手机做客户端与轻量引擎

DeepSeek Harness 桌面版由 Electron + Node 24 + Python 3.12 运行时组成，包含 node-pty、koffi（FFI）、sherpa-onnx 等原生依赖与桌面文件系统/进程沙箱。Android 无法直接复用这些组件；建议保留手机轻量引擎，完整 DSH 通过电脑版或云端远程执行。

引擎 DSH 0.2.1 · Node 24 手机 轻量引擎（现有） 远程 mobile-runs v2
1手机轻量引擎：对话 / 文档 / 插件 / 文件→ 2电脑版 DSH：完整工具 / 终端 / Office / 原生插件→ 3事件流 + 审批同步回手机→ 4云端执行：未启用（占位）

Review · 需要你拍板的几个点

先做什么、后做什么、哪些不做

下面是我建议的版本节奏与技术取舍。原型里的页面都是可实现的；真正的分叉点在「PPT 要做到什么程度」「插件是远程还是重写」「DSH 引擎是否需要在手机离线运行」。

建议 0.12 → 0.14不改变 0.11 已交付内容

01建议的版本节奏

三个方向拆成三步，每一步都能单独验收与回滚：

  • 0.12 · 文档能力：Markdown 导出 + Word / Excel 生成 + 资源文档中心 + 对话内动作（原型 01–04）。PPT 先出简版（4–8 张、纯文本/表格），不做动画与母版。
  • 0.13 · 插件移植：插件清单 + 手机原生 HTTP 工具（首批 12–20 个）+ 原生卡片 DSL + 权限页（原型 05–07）；技能类沿用现有导入。
  • 0.14 · 电脑版 DSH 远程：引擎设置 + DSH 会话（原型 08–10），复用 mobile-runs v2；不做手机端引擎打包。
  • 后续可选：Chaquopy 嵌入 Python 文档子集（高保真排版 / PDF），或 Node 子集；需要先看 0.12–0.14 的真实使用数据。
每步独立 APK 验收不改变现有账号/同步协议不新增底栏

02技术取舍

方向推荐方案限制结论
Word / Excel / PPTKotlin 原生写 OOXML（ZIP+XML）复杂版式、图表、公式保真度有限先做，覆盖 80% 场景
高保真 Office / PDF电脑版 DSH office-skills（python-docx / openpyxl / python-pptx）需要电脑在线，不能离线0.14 起作为补全
插件：技能类SKILL.md 直接导入现有技能库无执行逻辑0.13 即可用
插件：HTTP 工具Kotlin 重写接口 + 原生卡片每插件需实现与验收0.13 首批 12–20 个
插件：Python / 本地能力保留在电脑端，经连接桥远程调用依赖电脑在线不做手机原生 Python
DSH 引擎手机客户端 + 电脑/云端远程执行完整引擎不在 APK 内0.14，风险最低
DSH 整包嵌入Node/Electron + Python 重打包到 Android原生模块、体积、进程/沙箱限制、维护成本不建议近期做

03需要你确认

Q1 文档格式优先级是否按 MD → DOCX → XLSX → PPTX？（PPT 是否接受“简版手机生成 + 电脑精修”） Q2 首批插件范围：建议从 28 个里选 12 个手机可运行的 HTTP 工具（天气、空气质量、单位换算、二维码、IP、短链、百科、汇率、趋势、翻译…），是否认可？ Q3 插件入口放“工作台 → 扩展与插件”，文档放“资源 → 文档”，不新增第 5 个底栏 tab——是否同意？ Q4 引擎策略：完整 DSH 只通过电脑版/云端远程，不在手机 APK 内打包——是否接受？（若必须离线，需要单独立项评估体积与性能） Q5 文档是否需要“模板/品牌样式”（公司抬头、页眉页脚、编号），还是先做通用结构？

04风险与边界

  • 文档保真度：手机生成的 docx/xlsx/pptx 在 Office/WPS 中打开需抽样验证；复杂样式、图表、公式、批注不在首版范围。
  • 插件安全：HTTP 插件需要域名白名单与权限声明；远程插件沿用审批机制；不执行来源不明的二进制插件。
  • 离线边界：文档生成与手机插件可离线；电脑 DSH 与 Python 插件依赖电脑在线。
  • 体积：原生 OOXML 生成只增加少量代码；若后续引入 Python/Node 运行时，APK 会增加数十 MB，需单独评估。
  • 本原型为评审稿：示例数据与页面结构仅用于讨论，不代表已实现；所有入口与文案可在评审后调整。
